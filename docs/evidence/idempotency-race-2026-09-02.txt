Idempotency across replicas: before and after
=============================================

Date:        2026-09-02
Environment: macOS-26.2-arm64-arm-64bit | arm64 | CPython 3.12.2
Database:    PostgreSQL 15.15 (Homebrew), local unix socket
Reproduce:   INTENTGUARD_DATABASE_URL=postgresql:///<db> PYTHONPATH=src \
               python -m unittest tests.test_persistence.ConcurrentIdempotencyTest

The defect
----------
authorize_action read the stored authorization for a request_id and, on a miss,
issued a fresh reservation and lease. The engine's RLock made that check-then-act
atomic within one process and did nothing across two, which is the deployment
the project documents.

The daily cap was never breached -- every duplicate reservation was counted
against it -- which is why neither the adversarial suite nor the 8-process cap
test caught this. Both assert on the cap, and the cap was fine.
authorization_records also showed a single row, because _sync_authorizations
writes with ON CONFLICT DO UPDATE. The idempotency table looked correct while
the money did not.

Method
------
Eight replicas in separate OS processes (multiprocessing spawn), each with its
own PolicyEngine and its own in-process lock, sharing one Postgres. All eight
released from a barrier and called authorize_action with the same request_id
for 100. The agent's daily budget is 1,000,000 so that no duplicate is masked
by the cap refusing it.

Every replica returns the same reservation and the same lease. Seven duplicate
holds were created and given straight back, each carrying an
`authorization.duplicate_released` audit event naming the reservation that was
released and the one that won.

The fix
-------
StateRepository gains one indivisible operation:

    claim_authorization(request_id, request, result) -> bool

Postgres implements it as INSERT ... ON CONFLICT DO NOTHING ... RETURNING, so
exactly one caller gets a row back under concurrency. The in-memory repository
does the same check under its existing lock.

_issue_authorization_unlocked claims the request_id after reserving budget and
before keeping the reservation. A caller that loses releases its own hold, reads
the winning record, and returns that -- so a retried request_id resolves to one
reservation and one lease however many replicas answered it.

approve_action passes claim=False: it already owns the REVIEW record for that
request_id and is replacing it, not claiming it.

What this does not cover
------------------------
approve_action has the same check-then-act shape -- it reads the approval,
sees PENDING, and issues a lease -- so two concurrent approvals of one
request_id can still produce two reservations. Different code path, different
primitive (a conditional UPDATE on the approval row rather than an insert), and
deliberately not bundled into this commit. Not yet reproduced with a test.

Losing replicas still evaluate and reserve before discovering they lost. That
is wasted work under contention, not incorrect, and removing it needs the
per-entity read path in ADR 005.
